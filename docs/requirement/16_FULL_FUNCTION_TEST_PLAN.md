# 16 全功能测试计划（VK-FT）

版本：V1.0；日期：2026-11-08；编写：负责人。依据：01 产品需求、03 UI 框架、04/04A 公共 API、05–09 设计、11 测试与验收计划、15 技术决定、设计稿 `VideoKit_UI_Design_V1.0.pptx`（第 1–26 页）。

## 0. 目的与门槛

- 在 VK-M7（模块发布与宿主接入）和 VK-M8（App 发布）之前，对**全部功能**做一次完整、成体系的测试，覆盖功能、UI 布局、细节、边界和可预期的错误。
- **开始条件**：VK-M0–M6（含 VK-M5A）开发完成并冻结，**负责人先与用户确认后**才可开始（用户 2026-11-08 要求）。
- **通过条件**：§5 的退出标准全部满足。**全功能测试通过，才表示项目功能经过验证**，之后才进入 VK-M7、VK-M8 的打包与发布。
- 本计划不替代各里程碑的批次测试（TEST-Rn），而是在全部开发完成后，用同一个冻结版本把所有功能从头到尾再走一遍。

## 1. 原则

1. **冻结版本**：整轮测试只测一个冻结提交号和对应构建（App、example、embed 宿主），中途不换版本。发现的缺陷集中记录，测试轮结束后集中修复，再用新冻结版本做回归轮。
2. **按批次有序进行**：FT-01 → FT-14 依次执行。前一批出现 P1 阻塞时暂停后续批次，先修复。
3. **真机为准**：P0 需求必须在真机上 PASS；模拟器结果只作补充。至少两台真机：Android 12 中端机一台、较新旗舰机一台（芯片厂商不同），另加平板一台（多画面、编辑器展开布局）。**测试机由用户分配**，未分配前相关项记 NOT_RUN，不能计为通过。
4. **状态如实记录**：每个用例记 PASS / FAIL / BLOCKED / NOT_RUN，附设备、版本、证据（截图、录屏、日志）。不改写、不追认。
5. **缺陷分级**：P1 阻塞（崩溃、数据损坏、源文件被改、该打码未打码、头像错挂到他人、隐私外泄）；P2 主要功能错误；P3 次要功能或明显 UI 偏差；P4 细节与文案。
6. **源文件只读**：任何测试后源文件字节与路径不变（每批结束做 SHA-256 核对）。`test_media` 只读；需要修改或损坏的样本，一律复制到 `test-workspace\samples\` 下再处理。
7. **资源规则**：不与 Gradle 同时运行模拟器；按用户通知的时段执行。

## 5. 退出标准

1. 全部批次执行完毕；P0 需求相关用例在真机上 PASS。
2. 无未关闭的 P1、P2 缺陷；P3/P4 有明确处理决定（修复或用户同意延后）。
3. 源文件 SHA-256 全程不变；无网络上传；release 隔离通过。
4. NOT_RUN 项逐条列出原因，并经用户确认可接受（例如缺样本）。
5. 回归轮（修复后的冻结版本）对所有 FAIL 项与受影响用例复测通过。
6. 输出《全功能测试报告》（`reports\FT\REPORT.md`）：各批次结果、缺陷清单、证据索引、需求追踪（对照 `TRACEABILITY.csv`），交用户确认。

**用户确认测试报告后，进入 VK-M7、VK-M8。**

## 6. 组织与流程

- 执行：tester；必要时增派第二名 tester 并行执行互不依赖的批次（如 FT-05 与 FT-07）。
- 每批结束：tester 提交该批报告 → 负责人裁定缺陷 → 缺陷集中回交 coder（不逐条打断测试）。
- 回归轮：全部批次结束、缺陷修复冻结后，用新版本执行回归轮。
- 开始前：负责人检查开始条件（§0）、样本（§2.2）、设备（§2.1），**向用户确认可以开始**。
